V Vyora Security Architecture

Zero-knowledge by design

Business data is encrypted on the company's own device with a key Vyora never holds. The platform stores ciphertext it cannot read — not the owner, not staff, not an attacker with database access. Layered on top: row-level isolation, role-based access, tamper-evident audit, and device-bound sessions.

01

AES-256 encryption model

Record bodies are encrypted with AES-256-GCM on-device before they touch storage or the network. Only routing metadata (org_id, timestamps, version) stays in plaintext so the system can sync and isolate without reading content.

02

Secure key management

A key hierarchy separates the human secret from the data key. The passphrase never leaves the device; the server only ever sees a wrapped data key it cannot unwrap.

Secret
Owner passphrase / 24-word recovery code
never stored, never transmitted
↓ Argon2id KDF (per-org salt)
Wrapping key
KEK — key-encryption key
derived in memory on unlock, discarded on lock
↓ unwraps
Data key
DEK — random 256-bit, encrypts all records
stored only in wrapped form; server holds the wrapped blob

No passphrase, no data. Vyora cannot reset or recover a lost key — only the 24-word recovery code can. This is the cost of true zero-knowledge, and it is by design.

03

Row-level security & tenant isolation

Even before decryption, Postgres enforces that a request can only touch its own organisation's rows. Isolation is in the database, not just the app layer.

RLS policy
alter table invoices
  enable row level security;

create policy tenant_isolation
  on invoices
  using (
    org_id = auth.jwt()->>'org_id'
  );
One database, isolated tenants
org Asees only A's rows
org Bsees only B's rows
org Csees only C's rows
✕ cross-tenant read blocked at the DB

05

Audit logs

Every sensitive action is recorded append-only and hash-chained — each entry hashes the previous one, so any tampering breaks the chain and is detectable.
